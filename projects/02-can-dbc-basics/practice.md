# 手工对照练习

> 全部为虚构教学数据。无需编程、无需硬件；不要用于真实车辆。

## 1. 打开原始数据

在项目中点击 examples → sample_frames.csv。若下载到本地，用文本编辑器打开，避免表格软件把00变成0。CSV仅为对照表，不是ASC回放文件。

逐列看：message_id_hex是十六进制ID；dlc是数据字节数；data_hex是十六进制数据；expected列给出理论预期。先遮住最后两列。A行是0x321、1、00；B行是0x321、1、01。

## 2. 找到对应的DBC定义

打开 examples/demo_status.dbc，找到 BO_ 801 DemoStatus: 1 SimECU。801是0x321的十进制形式，1表示长度1字节，SimECU是虚构发送节点。该ID属于11位标准帧。

找到 SG_ ReadySt : 0|8@1+ (1,0) [0|1] "" SimVCU：

- 0|8：从起始位0开始，占8位，即完整的第0字节。
- @1+：Intel字节序、无符号。本例只有1字节，不展示跨字节差异。
- (1,0)：物理值=原始值×1+0。
- [0|1]：本例定义范围为0至1；不表示解析器会自动拦截其他数据。
- VAL_：把0、1映射为未就绪、已就绪。

## 3. 手动解析并核对

1. 确认两条数据的ID均匹配0x321，DLC均为1。
2. A行00转换为十进制0，应用比例与偏移得到0，再查VAL_得到未就绪。
3. B行01转换为十进制1，得到ReadySt=1，再查VAL_得到已就绪。
4. 与CSV预期列核对。以上是手算预期，不是软件实测。

## 4. 自测与答案

- 若DATA=02：原始值为2，超出本例定义范围，文字映射未定义；不能解释为已就绪。
- 若ID=0x322、DATA=01：本例没有对应定义，不能套用0x321的含义。
- 只有DATA=01能否判断车辆已就绪？不能，必须知道ID、帧类型和匹配的定义，且本例完全虚构。
- DBC会自己产生CAN数据吗？不会，它只是解释规则。

## 常见错误

| 现象 | 检查方法 |
| --- | --- |
| 找不到0x321 | DBC的BO_使用十进制801，不是十进制321 |
| 把01理解为通用就绪命令 | 状态含义只适用于本例定义 |
| CSV无法直接回放 | CSV是教学对照表，未提供ASC回放格式 |
| 状态只显示数字 | 工具可能未显示VAL_枚举文字，先核对数值0或1 |
| 中文映射乱码 | 文件使用UTF-8；核对工具支持的编码，先备份再另存副本 |
